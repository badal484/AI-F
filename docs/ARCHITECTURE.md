# Architecture

Living document — updated as each phase lands. See `docs/BUILD_PROGRESS.md` for phase status and `docs/DATABASE.md` for schema detail.

## Monorepo layout

npm workspaces, feature-sliced within each app.

```
apps/
  web/      Next.js (App Router) — serverless UI, deployed to Vercel
  worker/   Long-running Node process — Redis/BullMQ, deployed as a container/VM
packages/
  db/        Prisma schema, generated client, tenant-isolation extension
  shared/    Zod schemas, shared types, logger — used by both apps
  ai/        Vercel AI SDK provider abstraction, tool definitions, intent detection, reply drafting
  booking/   Availability computation, timezone math (Luxon), conflict-safe booking — used by both the dashboard UI and the AI's tools
  queue/     Shared Redis connection + BullMQ queue/job definitions — apps/web enqueues, apps/worker consumes
  whatsapp/  Meta Graph API client, webhook signature verification, inbound payload parsing
  automations/ Trigger → delay → action scheduling (Phase 9) — schedules AutomationRuns via packages/queue; apps/worker executes them
  billing/   Stripe client, Checkout/Portal session creation, webhook signature verification + event parsing, plan/price lookups (Phase 12)
  config/    Shared tsconfig/eslint base configs
```

`apps/web` and `apps/worker` are independently deployable: the UI runs serverless, the worker runs as a persistent process holding Redis/BullMQ connections. Both import `@aif/db`, `@aif/shared`, `@aif/ai`, `@aif/booking`, `@aif/queue`, `@aif/whatsapp`, `@aif/automations`, and `@aif/billing` (apps/web only — apps/worker has no billing-related job to run) as workspace packages so schema, types, validation, AI, booking, messaging, automation, and billing logic never drift between them — each lives in its own package (not inside `apps/web`) specifically so `apps/worker` can run the same logic. `@aif/ai` depends on `@aif/booking` (for the `checkAvailability`/`bookAppointment` tools) and `@aif/automations` (for `captureLead` to schedule LEAD_CREATED rules); `@aif/booking` depends on `@aif/automations` too (for `bookAppointment` to schedule APPOINTMENT_CREATED rules) — see "Automations (Phase 9)" below for why the scheduling call lives inside these shared packages rather than at each caller. `apps/worker`'s WhatsApp job processors depend on `@aif/ai`, `@aif/whatsapp`, and `@aif/queue` together.

**`apps/worker` runs via `tsx`, not a bundled `dist/`, in both dev and production** (`npm start` is `tsx src/index.ts`, same tool as `dev`) — this was a deliberate correction during Phase 8. The original Phase 1 setup bundled the worker with `tsup`/esbuild, which worked until this phase's code first imported `@aif/db` from within `apps/worker`: Prisma's generated client (and `pg`, `@prisma/adapter-pg`'s driver) both rely on dynamic `require()` internally, the same class of problem `pino` had in Phase 1 — but this time adding more packages to tsup's `external` list only uncovered further dynamic requires deeper in Prisma's own runtime, rather than fixing it. `tsx` transpiles per-file through Node's normal module resolution instead of statically inlining the whole dependency graph into one file, which sidesteps the entire bug class rather than chasing it. Runtime-verified before and after the fix (the pre-fix build produced a working artifact that crashed immediately on `node dist/index.js`) — see `docs/BUILD_PROGRESS.md`'s Phase 8 entry.

Within `apps/web/src`, code is organized by domain rather than by route:

```
app/                    Next.js routes — thin, delegate to domains/
domains/
  auth/                 session resolution, sign in/up/out actions, guard.ts (role gating), users.ts (list assignable staff — shared by crm and inbox), auth UI
  business-core/         tenant profile, locations (+hours), services, staff — actions + UI, per entity
  crm/                   customers, leads (+ pipeline stage), tags — actions + UI, per entity; shared.ts for cross-entity FK checks
  inbox/                 conversations (+ assignment/status), messages — actions + a two-pane chat UI
  ai-agent/               actions.ts wiring @aif/ai (intent detection, reply drafting) into the Inbox UI
  knowledge/              documents (chunk+embed on create) — actions + UI, including a test-search panel
  booking/                appointments — actions wiring @aif/booking + a find-a-time/confirm booking dialog
  whatsapp/               templates (config) + sendWhatsAppTemplateToConversation (day-to-day) — actions + UI
  automations/            rules (config) + reminders (day-to-day) — actions + UI
  widget/                 embed-snippet display only — widget config itself rides on business-core's tenantProfileSchema/updateTenantProfile (same precedent as whatsappPhoneNumberId), not a separate action file
  analytics/              getAnalyticsSummary — a single read-only aggregate query + a stat-card/bar-chart dashboard
  billing/                getBillingStatus/startCheckout/openBillingPortal — actions + UI, wiring @aif/billing
  platform-admin/         guard.ts (requirePlatformAdmin — a separate identity from tenant auth/guard.ts) + cross-tenant listTenants/getPlatformStats/setTenantSuspended actions, all via getPlatformDb()
components/ui/          shadcn/ui primitives only
lib/                    supabase clients, env helpers, utils
app/api/webhooks/       webhook receivers — thin: verify, parse, enqueue for apps/worker; no business logic here
app/api/widget/         public, unauthenticated widget message endpoint — origin-validated per tenant, replies synchronously (no queue — see "Website Widget" below)
app/api/webhooks/stripe/ Stripe webhook receiver — signature-verified, processes inline (no queue — see "Billing" below)
app/platform-admin/     cross-tenant admin UI — a separate route group from app/dashboard/, gated by requirePlatformAdmin(), not tenant auth (see "Platform Admin Dashboard" below)
```

## Server Actions as the data layer

CRUD domains (business-core, crm, inbox, and later phases) skip a separate REST/route-handler layer: Server Actions (`"use server"` functions under each domain's `actions.ts`) are called directly as TanStack Query `queryFn`/`mutationFn`, since a Server Action is just an async function that already runs server-side regardless of whether it's invoked from a `<form action>` or a client component's `fetch`-free call. This keeps Zod validation and tenant-isolation logic in one place instead of duplicating it across an API route and an action. List pages use `useQuery` + `useMutation` with optimistic cache updates (`queryClient.setQueryData`) per MASTER_INSTRUCTIONS.md §6; single-record forms (e.g. Settings) use `useMutation` alone.

Every read is wrapped in `requireTenantContext()` (any authenticated role), except billing status/actions (see below). Mutations split into two tiers — see `apps/web/src/domains/auth/guard.ts`: `requireWriteAccess()` (OWNER/ADMIN only) for *business configuration* (Tenant profile, Locations, Services, Staff, Tags, WhatsApp templates, Automation rules, and — Phase 12 — all of Billing, reads included, since who's on the subscription and what it costs is itself sensitive, not just changing it), and plain `requireTenantContext()` for *day-to-day work* (Customers, Leads, everything in the Inbox, Knowledge documents, Appointments, sending a WhatsApp template to a conversation, completing Reminders, and viewing Analytics) — `AGENT` exists specifically for that second tier, so gating it behind `requireWriteAccess()` would lock AGENT out of the job the role exists for. Reach for the right one deliberately when adding a new domain rather than defaulting to `requireWriteAccess()` for every mutation.

## Multi-tenant isolation

See `MASTER_INSTRUCTIONS.md` §4 for the governing rule and `docs/DATABASE.md` §"Tenant isolation" for the implementation. In short: `packages/db/src/tenant.ts` exports `getTenantDb(tenantId)`, a Prisma Client Extension that injects `tenantId` into every query against a tenant-scoped model. Application code never imports `PrismaClient` directly — only `getTenantDb()` or the narrowly-scoped `getPlatformDb()`.

## Auth

Supabase Auth (session cookies via `@supabase/ssr`). `apps/web/src/proxy.ts` refreshes the session on every request and redirects unauthenticated users away from `/dashboard`. `apps/web/src/domains/auth/session.ts` resolves the full `TenantContext` (tenant + role) server-side from the session — this is the only place that reads through `getPlatformDb()` outside the future Platform Admin phase, because tenant identity isn't known yet at that point.

## AI Core

`packages/ai` is the Vercel AI SDK integration (MASTER_INSTRUCTIONS.md §5), with the same "NOT CONFIGURED, not faked" discipline as every other integration:

- **Provider abstraction** (`src/provider.ts`) — `isAiConfigured()` / `missingAiEnvVars()` follow the same pattern as `apps/web/src/lib/env.ts`'s Supabase/DB checks. `getModel()` prefers Anthropic (`ANTHROPIC_API_KEY`, default model `claude-sonnet-5`, overridable via `AI_MODEL`) and falls back to OpenAI (`OPENAI_API_KEY`) if only that's set — `AI_MODEL` becomes *required* in that case rather than guessing an OpenAI model name. Every caller (`detectIntent`, `draftReply`) checks `isAiConfigured()` and throws a clear message rather than letting a missing key surface as an opaque provider error; the Server Actions that call them (`apps/web/src/domains/ai-agent/actions.ts`) check it again and return `{ error }` instead of ever calling into the SDK unconfigured.
- **Tools** (`src/tools/`) — each is a factory function closing over `tenantId` (and `conversationId` where relevant) so the AI can only ever act within the current tenant/conversation, using the exact same `getTenantDb()` isolation as every other domain — there is no separate "AI database access path." `getBusinessInfo` is read-only (Services/Locations/LocationHours, including their `id`s so later tool calls can reference them precisely); `captureLead`, `escalateToHuman`, and `bookAppointment` are real writes through the Phase 3/4 CRM/Conversation models and Phase 7's `@aif/booking`, wrapped in `$transaction` where they touch more than one table, per MASTER_INSTRUCTIONS.md §4.
- **`checkAvailability` / `bookAppointment`** — MASTER_INSTRUCTIONS.md §5's own example tools, built in Phase 7 once the `Appointment` model existed (they were deliberately deferred out of Phase 5 for this reason — see `docs/BUILD_PROGRESS.md`'s Phase 5 and 7 entries). Both call straight into `@aif/booking`, so the AI's booking path and the dashboard UI's booking path (`/dashboard/appointments`) are the *same* code, not two implementations that could drift — `bookAppointment` re-validates the slot inside a transaction rather than trusting whatever `checkAvailability` returned a moment earlier, and its tool wrapper reads the actual `{ booked: true | false }` result (not just "was the tool called") before reporting success back to `draftReply`'s caller, since a soft-fail here without that check would violate the "never fake actions" rule.
- **Intent detection** (`src/intent.ts`) — a `generateObject` call classifying a single message into `FAQ | BOOKING_REQUEST | LEAD_INTEREST | COMPLAINT | OTHER` plus a frustration flag, wired to a manual "Detect intent" button in the Inbox (not automatic-on-load, so an unconfigured AI doesn't produce an error toast just from opening a conversation).
- **Reply drafting** (`src/reply.ts`) — a tool-calling `generateText` loop (`stopWhen: stepCountIs(8)`, raised from 5 once booking added a longer typical tool chain: getBusinessInfo → checkAvailability → bookAppointment → text) that drafts a suggested reply into the compose box for a staff member to review and edit before sending — it never sends automatically and never creates a `Message` row itself. The system prompt includes today's date (for resolving "tomorrow"/"next Monday" before calling `checkAvailability`) and is explicit about prompt-injection defense (MASTER_INSTRUCTIONS.md §5): conversation history is treated as untrusted data, not instructions.

## RAG & Knowledge (Phase 6)

`packages/ai/src/rag/` — chunking, embedding, ingestion, and search, feeding a fourth tool (`searchKnowledgeBase`) into `reply.ts`'s tool set:

- **Chunking** (`chunk.ts`) — plain fixed-size character windowing with overlap, no LLM call.
- **Embeddings** (`embed.ts`) — always `OPENAI_API_KEY` + `text-embedding-3-small` (1536 dims), independent of whichever provider `getModel()` resolves for chat — Anthropic has no public embeddings API. Same `isEmbeddingConfigured()` / throw-with-clear-message pattern as `provider.ts`.
- **Storage** — `DocumentChunk.embedding` is a pgvector column, which Prisma can't represent as a normal field; see `docs/DATABASE.md`'s pgvector section for how it's isolated (a third, raw-SQL-based mechanism alongside `TENANT_SCOPED_MODELS` and `SELF_SCOPED_MODELS`).
- **Ingestion** (`ingest.ts`) — chunk → embed → store → set `KnowledgeDocument.status` to `READY` or `FAILED` (with a reason) — never left stuck at `PENDING`, never faked as successful if embeddings are unconfigured. Runs synchronously inside the `createDocument` Server Action; there's no background job queue wired up yet to move this off the request (that's Phase 8/9's worker infrastructure).
- **`searchKnowledgeBase` tool** — only added to `reply.ts`'s tool set when `isEmbeddingConfigured()` is true, so the AI never attempts a capability it doesn't have (same "don't offer what isn't configured" logic as Phase 4 not offering "AI" as a message sender).
- **UI** (`apps/web/src/domains/knowledge/`) — `/dashboard/knowledge`: add a document (title + pasted text, embedded synchronously on save), see its status/chunk count, and a "Test search" panel to see what the AI would retrieve for a given question, independent of an actual conversation.

## Booking Engine (Phase 7)

`packages/booking` — shared by the dashboard UI (`apps/web/src/domains/booking`) and the AI's `checkAvailability`/`bookAppointment` tools, so there's exactly one implementation of "what's actually bookable":

- **Availability** (`src/availability.ts`) — for a Service + Location + date (+ optional StaffMember), reads the Location's `LocationHours` for that weekday and its existing `Appointment`s, then generates candidate start times at a configurable interval (default 30 min) and filters out any that are in the past or overlap an existing appointment. All wall-clock math (interpreting `LocationHours`' `"HH:mm"` strings, generating candidate times) happens in the Location's own IANA timezone via [Luxon](https://moment.github.io/luxon/); results are converted to UTC only at the end. Runtime-verified directly against a known DST transition (`America/New_York`, 2026-11-01) and a busy-interval overlap case before wiring it into any UI — see `docs/BUILD_PROGRESS.md`'s Phase 7 entry.
- **Conflict scope, a deliberate scope decision:** if `staffMemberId` is given, only that person's own appointments block a slot. If omitted, *all* appointments at the Location block a slot — the Location is treated as having one concurrent booking at a time. Right for this platform's primary target (a single-practitioner local business); under-counts true parallel capacity for a Location with several independent staff, who should always be booked with an explicit `staffMemberId` to get accurate availability. A real multi-resource capacity model (e.g. "3 chairs, any of them") wasn't built — out of scope for Phase 7's baseline.
- **Booking** (`src/book.ts`) — `bookAppointment()` re-checks for a conflict inside a `Serializable`-isolation transaction immediately before creating the row (the slot the caller saw a moment earlier could be gone by now), and returns `{ booked: false, reason }` rather than throwing on a conflict — including a genuine Postgres serialization failure (`P2034`), which is caught and reported the same way. See `docs/DATABASE.md`'s "Booking conflict prevention" section for what this does and doesn't guarantee, and the ideal (unbuilt) fix.
- **UI** (`apps/web/src/domains/booking/`) — `/dashboard/appointments`: a "New appointment" dialog (pick service/location/staff/date → real available slots → confirm with customer details) and a list with an inline status control, following the same patterns as Leads/Conversations.

## WhatsApp Integration (Phase 8)

This is the phase that actually exercises MASTER_INSTRUCTIONS.md's "hybrid deployment" architecture: `apps/web` receives and enqueues, `apps/worker` does the real work.

- **Inbound flow:** Meta POSTs to `apps/web/src/app/api/webhooks/whatsapp/route.ts` → the route verifies `X-Hub-Signature-256` against `WHATSAPP_APP_SECRET` (`packages/whatsapp`'s `verifyWebhookSignature`, constant-time compare) → parses the payload (`parseInboundWebhook`, text messages only for this baseline — other message types are silently skipped, not guessed at) → resolves the tenant by the webhook's `phone_number_id` via `getPlatformDb()` (the third sanctioned use of it — see `docs/DATABASE.md`) → enqueues one `whatsapp-inbound` job per message (`packages/queue`) → acks 200 immediately. The route does no AI/DB work itself, on purpose: webhook handlers must ack fast, and Meta retries non-2xx responses.
- **`apps/worker/src/queues/whatsapp-inbound.ts`** does the actual work: finds/creates the `Customer` (exact phone match only — no E.164 normalization, a documented scope limit) and an open `Conversation`, records the `Message` (idempotent — see `docs/DATABASE.md`'s WhatsApp idempotency section), then — unless the conversation is already `HUMAN_REQUIRED` — calls `draftReply()` (the same Phase 5 function the Inbox's "Draft AI reply" button uses) and either enqueues the AI's reply for sending, or leaves it for staff if the AI escalated. This is the "communicate via WhatsApp" half of MASTER_INSTRUCTIONS.md's business vision actually closing the loop: real inbound message → AI grounded in real tenant data and tools → real reply sent back, or a real human handoff.
- **Outbound flow, one choke point:** both staff-composed replies (`apps/web`'s `sendMessage`, when a conversation's `channel` is `WHATSAPP`) and AI-drafted auto-replies (the inbound processor above) enqueue into the *same* `whatsapp-outbound` queue rather than calling the WhatsApp API themselves — `apps/worker/src/queues/whatsapp-outbound.ts` is the only place `sendTextMessage()` is actually called, so retry/rate-limit behavior only needs to live in one place. **Deliberate, documented exception:** manually sending a *template* message (`sendWhatsAppTemplateToConversation`) calls `sendTemplateMessage()` directly from the Server Action instead of going through the queue — it's a low-frequency, explicit staff action, not an automated reaction, so stretching the queue's "one choke point" principle to cover it wasn't worth the complexity.
- **Idempotency** (MASTER_INSTRUCTIONS.md §4) is two layers deep: a BullMQ job-id dedupe (`wa-inbound:${waMessageId}`) catches most Meta webhook redeliveries before a second attempt even starts, and the `Message` table's `@@unique([tenantId, externalId])` constraint is the final guard if one slips past that. See `docs/DATABASE.md`.
- **Message templates** — `WhatsAppTemplate` is a local registry staff fill in to match what Meta already approved (not synced automatically — no Meta API integration for reading templates back was built). Required outside Meta's 24-hour customer-service window, when a free-form send would be rejected; the outbound worker doesn't auto-detect a closed window and switch to a template on its own (that would require guessing Meta's actual rejection error shape without live credentials to confirm it) — staff trigger a template send explicitly from the Inbox when they know it's needed.
- **Not built:** media/attachment messages (images, documents, location, etc. — text only), delivery/read-receipt status tracking (Meta sends these as separate webhook events), and a true multi-resource capacity model for who can receive an inbound conversation (mirrors the same scope decision `packages/booking` made in Phase 7).

## Automations (Phase 9)

`packages/automations` (`src/schedule.ts`) is Phase 9's "Triggers, Delays, Reminders" engine: a tenant-configured `AutomationRule` says *when* X happens, wait N minutes, then do Y. Scheduling is event-driven — fired from inside the real write path the moment the trigger actually happens — never a poll/cron:

- **`scheduleAutomationRuns(event)`** — called from three places: `packages/booking`'s `bookAppointment()` (`APPOINTMENT_CREATED`, the same single shared implementation both the dashboard and the AI's `bookAppointment` tool call — see "Booking Engine" above, the same reasoning extends here for free), `apps/web/src/domains/crm/leads/actions.ts`'s `createLead`/`updateLeadStage` (`LEAD_CREATED`/`LEAD_STAGE_CHANGED`), and `packages/ai`'s `captureLead` tool (`LEAD_CREATED` — leads created by the AI don't go through the dashboard action, so this trigger needs its own call site). It finds every enabled `AutomationRule` matching the trigger (and, for `LEAD_STAGE_CHANGED`, the specific stage), computes each one's fire time, and enqueues a delayed BullMQ job (`packages/queue`'s `automation-run` queue) per rule via `AutomationRun`, one row per (rule, entity) pair.
- **Delay semantics differ by trigger, deliberately:** for `APPOINTMENT_CREATED`, `delayMinutes` counts *backward* from the appointment's `startAt` (a reminder sent before it starts); for `LEAD_CREATED`/`LEAD_STAGE_CHANGED`, it counts *forward* from the moment the trigger fired (a follow-up sent after). A reminder whose computed fire time has already passed (e.g. an appointment booked to start sooner than the rule's lead time) is recorded as `SKIPPED`, not fired late.
- **Idempotency and cancellation both live on `AutomationRun`**, not by managing the BullMQ job directly: `@@unique([ruleId, entityId])` means a rule fires at most once per entity (even across repeat lead-stage transitions — a documented tradeoff favoring "don't spam" over "always re-fire"), and cancelling (e.g. `updateAppointmentStatus` setting `CANCELLED`) just flips still-`PENDING` runs to `CANCELLED` in the DB — the worker checks status at fire time rather than the harder problem of reaching into BullMQ to remove a specific delayed job.
- **`apps/worker/src/queues/automation-run.ts`** re-fetches the run and its rule fresh at fire time (never trusts the job payload beyond `tenantId`/`runId`), resolves the target entity (an `Appointment` or `Lead`, depending on the rule's trigger) back to a phone number/customer/lead, then executes the action: `SEND_WHATSAPP_TEMPLATE` calls `sendTemplateMessage()` directly (not through the `whatsapp-outbound` queue — that queue exists to serialize sends tied to a `Message`/`Conversation` row, and automation sends deliberately don't create one, see "Known, accepted limitations" below), or `CREATE_REMINDER` writes a staff-facing `Reminder` row. Action failures are re-thrown so BullMQ's configured retries get a chance at transient errors (same as `whatsapp-outbound.ts`); `AutomationRun.status` is only written to `FAILED` once retries are exhausted, via a `worker.on("failed", ...)` listener that checks `job.attemptsMade` against `job.opts.attempts` — a mid-retry attempt failure must not look "already handled" to the next attempt.
- **Known, accepted limitation:** automation-sent WhatsApp messages are *not* logged as a `Message` into the Inbox — the audit trail is the `AutomationRun` row (`status`/`error`) instead. Considered logging into a Conversation (mirroring the inbound/outbound worker pattern) but that requires resolving/creating a Conversation for two different entity shapes (Appointment vs Lead) and a new `MessageSender` value, which felt like scope creep for this phase's actual deliverable (the rule engine itself); revisit if staff need automation sends visible in-thread. Also: no dynamic `{{n}}` template variable substitution for automation-triggered sends (always empty `bodyParams`) — use a placeholder-free template, or send manually via the Inbox for anything needing per-customer variables.
- **UI** (`apps/web/src/domains/automations/`) — `/dashboard/automations`: create/enable/disable/delete rules (config-tier, `requireWriteAccess`), with the trigger/action/template fields shown conditionally. `/dashboard/reminders`: a flat list of open (`isCompleted: false`) Reminders with a "mark done" action (day-to-day tier, `requireTenantContext`) — no reminder history view yet, only what's still open.

## Website Widget (Phase 10)

An embeddable chat widget any tenant can add to their own website — the first customer-facing surface in this repo that isn't the dashboard, and the first one with no Supabase session to authenticate a request with, which is what makes "origin validation" (MASTER_INSTRUCTIONS.md's own phrasing for this phase) the actual security boundary rather than an afterthought:

- **Embed mechanism, and why it's a script tag, not an iframe.** A tenant pastes `<script src="https://<app-domain>/widget.js" data-tenant-id="..." async></script>` into their site. `apps/web/public/widget.js` is deliberately plain, dependency-free JS (no React/Next build step — it runs inside an arbitrary third-party page, not this app, so it can't assume that page's bundler or globals) that injects a floating chat bubble directly into the host page via a Shadow DOM (`element.attachShadow`), which fully isolates its styles from the host page's CSS in both directions without needing an iframe. This matters for *why* origin validation is meaningful here: because the widget's JS executes in the host page's own origin, its `fetch()` calls to our API carry that page's real `Origin` header — a genuine, browser-enforced CORS boundary, not a self-reported value. (An iframe-based widget would make every widget request same-origin to *our* domain instead, and origin validation would only be able to gate who's allowed to *embed* the iframe, not who's allowed to *use* it — a weaker guarantee for this phase's actual goal.)
- **`Tenant.widgetEnabled` + `Tenant.widgetAllowedOrigins`** (configured at `/dashboard/settings`, same place `whatsappPhoneNumberId` already lives — one tenant-config page, not a new one per integration) are checked on every widget request, not just at embed time: `POST /api/widget/[tenantId]/message` and its `OPTIONS` preflight both call `resolveAllowedOrigin()`, which looks up the tenant (via `getPlatformDb()` — the fourth sanctioned use, see `docs/DATABASE.md`) and rejects unless `widgetEnabled` is true and the request's `Origin` header exactly matches an entry in `widgetAllowedOrigins`. Rejections are deliberately generic (a 403 that doesn't distinguish "no such tenant" from "origin not allowed") so the endpoint can't be used to enumerate tenant ids.
- **`tenantId` lives in the URL path (`/api/widget/[tenantId]/message`), not the request body — this is load-bearing, not stylistic.** A CORS preflight (`OPTIONS`) request never carries the actual `POST` body, so if origin validation needed the tenantId to look up that tenant's specific allowlist, it would have nothing to check against during preflight. Putting `tenantId` in the path makes it available to `OPTIONS` via route params before any body exists. The real `POST` handler re-validates independently anyway (never trusts that a browser actually honored its own preflight result) — same defense-in-depth reasoning `getTenantDb()`'s injected-plus-explicit `tenantId` already uses elsewhere in this codebase.
- **Synchronous reply, unlike WhatsApp's enqueue-and-ack pattern.** There's no third-party redelivery to guard against here (unlike a Meta webhook), and the visitor's browser is sitting there waiting on the response — `POST /api/widget/[tenantId]/message` finds/creates a `Conversation` (`channel: WEBSITE`, correlated to the same anonymous visitor across messages via `widgetVisitorId` — a client-generated id persisted in the visitor's own `localStorage`, not a cookie, since a cookie set by our API's response would be a third-party cookie in the host page's context and increasingly blocked by browsers), logs the `Message`, calls the same `draftReply()` Phase 5/8 already use, and returns the reply text directly in the response body. No queue, no `apps/worker` involvement at all for this flow.
- **Graceful degradation, not fabricated replies:** if AI is NOT CONFIGURED, or the conversation is already `HUMAN_REQUIRED`/gets escalated mid-reply, the endpoint returns a real (not-invented-content) fallback string — the visitor's message is still genuinely saved either way, just without an automatic reply, which is what actually happened.
- **Accessibility** (MASTER_INSTRUCTIONS.md §"Mobile-First Accessibility" explicitly names the Web Widget): the bubble button and panel carry proper ARIA roles (`role="dialog"`, `aria-modal`, `role="log"`/`aria-live="polite"` on the message list so screen readers announce new replies), full keyboard operability (Enter to send via a real `<form>`, Escape to close and return focus to the bubble button, focus moves into the input on open), and a mobile breakpoint where the panel becomes full-screen rather than a small fixed box.
- **Not built (deferred, not forgotten):** rate limiting / anti-abuse beyond basic input length caps — Origin validation stops a real browser from using the widget off an unauthorized site, but can't stop a direct scripted POST with a forged `Origin` header, since only real browsers enforce that header's integrity; genuine abuse protection (per-tenant/per-visitor rate limits, possibly a CAPTCHA) belongs in Phase 14 (Security Hardening), and building it piecemeal now would preempt that phase's own design. Also not built: wildcard/subdomain origin matching (exact string match only), and multi-language/RTL widget UI.

## Analytics & AI Evaluation (Phase 11)

MASTER_INSTRUCTIONS.md names this phase "Usage tracking, failure rates." Both halves are built on data this app already produces as a side effect of real work — nothing here is a separate tracking pipeline or fabricated metric:

- **`AiInteractionLog`, written by `draftReply()` itself** (`packages/ai/src/reply.ts`), not by its callers — the same "one shared implementation, so every caller gets it for free" reasoning already used for `bookAppointment` (Phase 7) and `scheduleAutomationRuns` (Phase 9). This means the Inbox's manual "Draft AI reply" button (Phase 5), the WhatsApp inbound worker (Phase 8), and the website widget (Phase 10) are *all* captured automatically — none of those three call sites needed to change.
- **`bookingAttempted` is tracked separately from `booked`**, added to `DraftReplyResult` this phase specifically so "no booking was ever attempted" and "a booking was attempted and failed" don't both collapse into `booked: false` — the difference is exactly what "failure rates" needs to be meaningful (a booking *success rate* only makes sense as a fraction of attempts, not of all AI replies).
- **Failures are logged too, not just successes.** `draftReply()` now wraps its `generateText()` call in a try/catch: on failure, it writes an `AiInteractionLog` row with `error` set and *still re-throws* — draftReply()'s existing throw-on-failure contract for its three callers is unchanged, this is a pure additive observability side effect. A failure to write the log itself is caught and logged separately, never allowed to mask or replace the original AI error.
- **Deliberately not logged: "AI is NOT CONFIGURED."** Every caller already checks `isAiConfigured()` before calling `draftReply()` at all and logs that separately via `logNotConfigured()` — folding it into `AiInteractionLog` too would conflate a deployment/config gap with an actual runtime failure of a real AI call, which are different failure classes worth keeping apart.
- **`apps/web/src/domains/analytics/actions.ts`'s `getAnalyticsSummary()`** — a single read-only aggregate: conversations grouped by channel, leads grouped by pipeline stage, appointments grouped by status (all via Prisma's `groupBy`, tenant-scoped like every other query), plus the AI evaluation numbers derived from `AiInteractionLog` (escalation rate, lead-capture rate, booking success rate among attempts, failure rate, average response time). `zeroFillCounts()` merges the groupBy results against the full known set of stages/channels/statuses (`@aif/shared`'s existing `LEAD_STAGES`/`CONVERSATION_CHANNELS`/`APPOINTMENT_STATUSES` constants) so a stage nobody has reached yet still renders as a zero bar instead of silently vanishing from the chart.
- **UI** (`/dashboard/analytics`) — plain CSS width-percentage bars for the breakdowns, not a charting library; this repo has none installed yet and one stat dashboard isn't sufficient reason to add one. Read-only, day-to-day tier (`requireTenantContext`) — there's nothing to configure here, only to look at, so it doesn't belong behind `requireWriteAccess()`.
- **Not built:** any time-series/trend view (the schema stores `createdAt` on every relevant row, so this is addable later without a schema change — just not built now), per-conversation or per-staff-member breakdowns, and cost/token tracking (the AI SDK's usage data wasn't threaded through — would need `generateText`'s `usage` field captured alongside the rest, deferred since no billing feature yet depends on it — see Phase 12).

## Billing (Phase 12)

`packages/billing` wraps the Stripe SDK — MASTER_INSTRUCTIONS.md's "Stripe SaaS architecture":

- **Stripe Checkout for subscribing, the Stripe-hosted Customer Portal for everything else** (payment method changes, invoice history, self-service cancellation) — this app never collects or stores card details itself, and never builds card-management UI, which would pull it into PCI scope for no real benefit over Stripe's own already-compliant hosted pages.
- **The Stripe Customer is created synchronously, before redirecting to Checkout — not deferred to a webhook.** `startCheckout()` (`apps/web/src/domains/billing/actions.ts`) calls `getOrCreateStripeCustomer()` and saves `Tenant.stripeCustomerId` to the DB immediately. This closes a real ordering gap: Stripe doesn't guarantee webhook delivery order, so if `stripeCustomerId` were only ever set by processing `checkout.session.completed`, a `customer.subscription.updated` event could arrive first and have no tenant to resolve to.
- **Idempotency (MASTER_INSTRUCTIONS.md's "Webhooks... must be strictly idempotent") is achieved differently here than for WhatsApp — deliberately, not as an oversight.** WhatsApp's inbound webhook needed a dedup layer (BullMQ job-id + a DB unique constraint) because processing it means *creating* a `Message` row, which isn't naturally safe to repeat. Stripe's webhook only ever *upserts* `Subscription` keyed on `tenantId` (`@unique`) — replaying the same event just re-writes the same target state, which is idempotent by construction. No separate processed-event-id table was built, because none is needed for what this handler actually does.
- **Processed inline, synchronously, like the website widget — not enqueued for `apps/worker`, unlike WhatsApp.** The work here is a couple of DB upserts, no AI calls; there's nothing to gain from a queue and Stripe (like Meta) wants a fast ack.
- **Real prices, never hardcoded ones.** `/dashboard/billing` shows each paid plan's actual price by calling `stripe.prices.retrieve()` at request time (`packages/billing/src/plans.ts`'s `listPlanPricing()`), not a dollar figure written into this codebase — a hardcoded price could silently drift from whatever's actually configured in the Stripe Dashboard, which is exactly the kind of fabricated fact MASTER_INSTRUCTIONS.md §7 forbids. A plan whose price env var isn't set (or doesn't resolve) shows as "Not configured," never a guess.
- **`SubscriptionStatus` mirrors Stripe's own status values 1:1** (`TRIALING | ACTIVE | PAST_DUE | CANCELED | UNPAID | INCOMPLETE | INCOMPLETE_EXPIRED | PAUSED`, verified against stripe@22.5.0's own type defs), rather than collapsing them into a smaller set — a lossy mapping (e.g. treating `paused` as `active`) would misrepresent real billing state to staff looking at `/dashboard/billing`.
- **Not built:** any feature gating tied to plan/subscription status. `Subscription.status` is tracked and displayed but nothing in this app currently checks it before allowing a feature — MASTER_INSTRUCTIONS.md's terse phase description doesn't specify what a `PAST_DUE` or `CANCELED` tenant should lose access to, and guessing that policy (rather than it being a real product decision) felt like exactly the kind of thing not to fabricate. Also not built: usage-based/metered billing, multiple simultaneous subscriptions per tenant, proration UI (Stripe's own Checkout/Portal handle this), and annual billing options.

## Platform Admin Dashboard (Phase 13)

The first genuinely cross-tenant surface in this app — everywhere else, "tenant" is the unit of isolation; here, seeing across all of them at once is the entire point.

- **`PlatformAdmin` is a new, separate identity — not a special `User.role` value.** A `User` row is inherently scoped to exactly one `tenantId` (it's a `TENANT_SCOPED_MODEL`), but a platform admin oversees every tenant, so there's no single `tenantId` a "super role" could live under without breaking that model's own meaning. `PlatformAdmin` links to the same Supabase Auth (same `supabaseUserId` pattern as `User`, same login page — there's no separate platform-admin login flow), but is a wholly separate row in a wholly separate table, checked by `requirePlatformAdmin()` (`apps/web/src/domains/platform-admin/guard.ts`), never `requireTenantContext()`/`requireWriteAccess()`.
- **No self-serve or in-app way to create a `PlatformAdmin` row — deliberately, not a missing feature.** Exposing any UI or action that could create one would be a privilege-escalation path (anyone who could reach that action could grant themselves cross-tenant access to every business on the platform). The only way to provision one is direct DB access (e.g. `npx prisma studio -w @aif/db`, or a manual `INSERT`) by someone who already has that level of trust — the same root-of-trust bootstrapping problem every real platform has for its first admin account, not unique to this app.
- **`getTenantDb()` now refuses to query any model that's neither tenant-scoped nor self-scoped**, rather than silently passing the query through unscoped — a defensive tightening made *because of* adding `PlatformAdmin` (the first model that's genuinely neither), not a pre-existing behavior. Before this phase, every model in the schema was one or the other, so the gap was latent but unreachable; `PlatformAdmin` (and the still-inert `Agency`) made it reachable, so `packages/db/src/tenant.ts`'s extension was tightened to throw instead. See that file's own doc comment for the reasoning.
- **Tenant suspension is real enforcement, applied at every entry point that already resolves a Tenant row — not just a cosmetic flag.** `setTenantSuspended()` sets `Tenant.isSuspended`/`suspendedAt`. Three places check it: `resolveTenantContext()` (blocks the entire dashboard — see below for why it still returns a context rather than null), the WhatsApp webhook route (silently drops inbound messages for a suspended tenant, same as it already does for an unmapped phone number), and the website widget's origin resolution (a suspended tenant's widget stops accepting messages, same code path as an unconfigured/disabled widget).
- **`resolveTenantContext()` returns a real context for a suspended tenant, with `isSuspended: true` — not `null`.** Returning `null` would make the dashboard's existing `if (!context) redirect("/login")` fire, silently bouncing a legitimately-authenticated user back to a login form with zero explanation (confusing, and for a still-valid session, potentially a redirect loop). Instead, `requireTenantContext()` throws a clear "workspace has been suspended" `UnauthorizedError` — which every action already catches and surfaces via the exact same `{ error }` pattern used for every other failure — and the Overview page (`/dashboard`, the one place that calls `resolveTenantContext()` directly rather than through `requireTenantContext()`) renders a dedicated suspended-workspace message instead of redirecting.
- **Platform-wide stats reuse the same `groupBy` approach as Phase 11's tenant-level Analytics**, just unscoped (`getPlatformDb()` instead of `getTenantDb()`) — `getPlatformStats()` counts tenants by plan tier, backing FREE out of the total rather than querying for it directly, since a tenant with no `Subscription` row is implicitly FREE and has no groupBy row of its own.
- **Not built:** any UI/flow for creating an Agency or attaching Tenants to one (Agency stays inert until Phase 18, per its own doc comment in `schema.prisma`); a distinct "access denied" page for an authenticated-but-not-admin visitor to `/platform-admin` (they see the plain login form again instead — a known UX rough edge, not a security gap, since `requirePlatformAdmin()` is still the actual gate); and any audit log of suspend/reactivate actions beyond `Tenant.suspendedAt`.

## Security Hardening (Phase 14)

MASTER_INSTRUCTIONS.md names this phase with no further detail — interpreted as: close the concrete, already-identified gaps this codebase itself flagged along the way (rather than a generic security checklist), plus a proper investigation of the one standing `npm audit` finding this repo had been carrying since Phase 9.

- **Rate limiting on the website widget's message endpoint** (`packages/queue/src/rate-limit.ts`'s `checkRateLimit`, a Redis `INCR`+`EXPIRE` fixed-window limiter) — the gap Phase 10's own docs explicitly flagged as deferred here: origin validation stops a real browser from using the widget off an unauthorized site, but a request that passes every check still does real, cost-incurring work (a DB write, an AI call), so unlimited volume from a technically-legitimate origin was still a real cost/abuse vector. Two limits, both checked on every `POST /api/widget/[tenantId]/message`: per-visitor (tight — a real chat rarely needs more than 10 messages/minute) and per-tenant (loose — only matters if abuse spreads across many `visitorId`s, since a single visitor can't reach it without tripping their own limit first). Verified against a real local Redis instance (allow-up-to-limit, reject-beyond, remaining-count accuracy, and window-expiry reset) before wiring it in. If Redis is NOT CONFIGURED, rate limiting degrades to "not enforced" (logged, not silently skipped) rather than blocking every widget request outright — origin validation remains the primary defense either way; this is one more layer on top, not the only one.
- **Security response headers** (`apps/web/next.config.ts`'s `headers()`): `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (denying camera/microphone/geolocation, none of which this app uses). **The CSP deliberately does not use nonces** — Next's own docs are explicit that nonce-based CSP requires forcing *every* page to dynamic rendering (disabling static optimization entirely), a real architecture/performance tradeoff that this environment has no way to verify visually (no live Supabase session to actually load and inspect a real authenticated dashboard page in a browser). Shipping an unverified CSP change that could silently break the whole dashboard felt like a worse outcome than a real, if less strict, policy — so this uses Next's own documented "Without Nonces" baseline instead. `'unsafe-inline'` is present on both `script-src` and `style-src`: the latter isn't optional even with more effort, because React's `style={{...}}` prop (used throughout this app's bar-chart UI — `domains/analytics`, `domains/automations`) renders as inline `style=""` *attributes*, and CSP has no nonce mechanism for style attributes, only for `<style>` elements — only removing every inline style app-wide would allow a strict `style-src`, out of scope here. Even with `'unsafe-inline'`, this is real protection, not a token gesture: it blocks loading scripts/stylesheets/objects/frames from any external origin, restricts `<base>`/`<form>` targets, and `frame-ancestors 'none'` reinforces (doesn't conflict with) Phase 10's own decision to embed the widget via a `<script>` tag rather than an iframe. `connect-src` includes `NEXT_PUBLIC_SUPABASE_URL` when configured, since Supabase's browser client makes direct `fetch()` calls to it for session refresh — omitting it would have silently broken login.
- **`npm audit`'s standing finding, actually investigated this time, not just re-noted.** `deepmerge-ts` (via `@prisma/config` via the `prisma` CLI package) has a real advisory (stack exhaustion on deeply nested input). Confirmed dev-only exposure concretely, not just by dependency-tree reasoning: `prisma` is a `peerDependency` of `@prisma/client` (optional, per its own `peerDependenciesMeta`) and lives in `packages/db`'s `devDependencies`, never `dependencies`; grepping the generated Prisma client source and the actual `apps/web` production build output (`.next/`) for any reference to `"prisma"` or `"@prisma/config"`/`deepmerge-ts` turned up nothing — this vulnerability's code never ships in what's actually deployed. `npm audit fix --force` would downgrade to `prisma@6.12.0`, which conflicts with this repo's deliberate Prisma 7 driver-adapter architecture (see "Documented deviations" below) — fixing a vulnerability with zero production exposure by downgrading a load-bearing dependency would be a net regression. Accepted, not fixed; re-check if `@prisma/config`/`deepmerge-ts` ever appear in `npm ls prisma --omit=dev`'s actual runtime resolution (not just the peer-dependency tree `npm ls` prints either way).
- **Also checked, nothing found:** no `dangerouslySetInnerHTML`, `eval()`, or `new Function()` anywhere in the codebase (grepped); no stray `console.log`/`console.error` of potentially sensitive data outside the structured pino logger (grepped) — `apps/web/public/widget.js`'s one `console.error` only logs a client-side configuration error (missing `data-tenant-id`), nothing sensitive.
- **Not built:** a stricter nonce-based CSP (see above — a real, disclosed tradeoff, not an oversight); `Strict-Transport-Security` (Vercel, this app's target deployment platform, adds HSTS automatically at the edge for custom domains over HTTPS — adding it here too would be redundant and, if ever self-hosted over plain HTTP in a dev/staging context, actively wrong); rate limiting on the Stripe/WhatsApp webhook routes (both are gated by signature verification, which is cheap to check and reject before any real work happens — a materially different risk profile than the widget endpoint, where a request can pass every check and still be expensive); a CI-level `npm audit`/dependency-scanning gate (that's Phase 15 — Production Infrastructure & CI/CD's job, not this one's).

## Production Infrastructure & CI/CD (Phase 15)

MASTER_INSTRUCTIONS.md names this phase with no further detail; interpreted as: finally build the deployable artifacts for the "hybrid deployment" split the architecture has assumed since Phase 1 (§4 — `apps/web` serverless, `apps/worker` persistent), plus a CI pipeline that runs the exact verification loop every phase of this build has been doing manually. Full detail in `docs/DEPLOYMENT.md`; summarized here:

- **`.github/workflows/ci.yml`** — install, generate the Prisma client (schema-only, no live DB needed — same as every `npm run build` this repo has ever run), typecheck, lint, build, on every push to `main` and every PR. Runs with **zero secrets**, deliberately — every integration in this app degrades to a logged NOT CONFIGURED state with no credentials at all, so the build genuinely doesn't need any to succeed. **This workflow was verified by actually running its exact sequence locally**, not just checked for valid YAML: deleted `packages/db/src/generated/` (simulating a fresh checkout, since it's gitignored), ran `npm ci` → `npm run db:generate` → `npm run typecheck` → `npm run lint` → `npm run build` in that order, all clean.
- **`apps/worker/Dockerfile`** — `node:24-alpine`, whole-repo `COPY . .` (build context must be the repo root, not `apps/worker` — npm workspaces need every workspace's `package.json` to resolve; see the Dockerfile's own comment), `npm ci`, `npm run db:generate`, then `npm run start` (the same `tsx src/index.ts` command already used and verified in every prior phase — no separate bundle/build step, consistent with Phase 8's tsup→tsx architecture correction). **Unverified** — this environment has no Docker to actually run `docker build` against it; written carefully and cross-checked against `apps/worker/package.json`'s real scripts, not guessed.
- **`docker-compose.yml`** — local Postgres via the `pgvector/pgvector` image specifically (confirmed via Docker Hub, not assumed — a vanilla `postgres` image lacks the `vector` extension binary, so `CREATE EXTENSION vector` would fail against it) plus Redis, for local development. **Also unverified** for the same Docker-unavailability reason — but this is the first point in this repo's build history where a real local Postgres becomes an *option* for whoever has Docker where they're working; every "unverified against a live database" caveat in every prior phase's docs exists specifically because this build environment has neither Docker nor a reachable Postgres.
- **Not built, deliberately:** an actual CD (deploy) workflow. Wiring one up needs a real Vercel token/project and a real worker-host redeploy trigger, neither of which exist in this environment — fabricating a deploy job with placeholder secrets that has never deployed anything would be exactly the "no fake implementations" violation MASTER_INSTRUCTIONS.md §7 warns against. Vercel's own GitHub integration (connect the repo in the dashboard, it deploys on push automatically) is the standard path once a real project exists, and needs no committed workflow file. Also not built: a worker health-check endpoint (most container hosts want one for liveness probes; `apps/web` has `/api/health`, `apps/worker` doesn't — flag this if deploying somewhere that requires it), and a CI-level dependency/container vulnerability scanning gate (Phase 14 investigated this repo's one standing `npm audit` finding but didn't add an automated gate for future ones — no established severity policy to gate on yet).

## Documented deviations from MASTER_INSTRUCTIONS.md §3

Approved exceptions to the exact stack named in MASTER_INSTRUCTIONS.md, each because the tool's current released behavior differs from what was specified:

- **Radix Primitives → Base UI.** The shadcn/ui CLI (v4.18, current as of this phase) now generates components on top of [Base UI](https://base-ui.com), Radix's own successor library (same maintainers), not `@radix-ui/react-*`. Approved by the product owner 2026-08-19 rather than pinning an older shadcn CLI version. Base UI's polymorphism API is a `render` prop (`<Button render={<Link href="/x" />}>`) instead of Radix/shadcn's older `asChild` + `Slot` pattern — use `render`, not `asChild`, in any new component built on these primitives.
- **Prisma 7 driver adapters.** Prisma 7 removed `url`/`directUrl` from the `datasource` block in `schema.prisma` entirely; connection configuration now lives in `packages/db/prisma.config.ts`, and `PrismaClient` is constructed with an explicit adapter (`@prisma/adapter-pg`, node-postgres) rather than the built-in Rust query engine. This is Prisma's current recommended setup, not a deviation from a documented stack choice, but is called out here because it changes how `DATABASE_URL` is wired: there's a single `DATABASE_URL` (no separate `DIRECT_URL`) and it should be a **direct/session** connection string, not a pgbouncer transaction-pooler URL — `prisma migrate` needs session-level features that transaction pooling doesn't support.
- **Next.js `middleware.ts` → `proxy.ts`.** Next.js 16 renamed the `middleware` file convention to `proxy` (same capability — session refresh, route protection — new name/export). `apps/web/src/proxy.ts` uses the current convention.
- **Meta Graph API version.** `packages/whatsapp/src/client.ts` defaults to `v25.0`, confirmed current by fetching Meta's own docs directly on 2026-08-19 rather than assuming a remembered version (an older SDK's docs, also fetched during that research, referenced `v16.0` — this API version genuinely drifts over time). Overridable via `WHATSAPP_API_VERSION` without a code change; re-verify against Meta's docs before relying on the default once real credentials are configured.
- **Stripe API version, and a genuine breaking change caught by checking.** `packages/billing/src/client.ts` pins `2026-07-29.dahlia`, read directly from `stripe@22.5.0`'s own generated type defs rather than assumed. This mattered concretely: that same check showed `Stripe.Subscription` no longer has a top-level `current_period_end` field in this API version — it moved to `subscription.items.data[].current_period_end` — which would have been a silent wrong-value bug (not a type error; both are `number`) if written from memory instead of verified. Re-check `node_modules/stripe/esm/apiVersion.d.ts` and `resources/Subscriptions.d.ts` before relying on either if the `stripe` dependency is ever upgraded.
